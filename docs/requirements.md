# 需求：MoSCoW 排序

三個面向共用這一張表。「適用分頁」標示需求屬於預調度、情境評估，或兩頁共用；新增需求一律加在這裡，不另開表格。需求狀態與所有版本的可驗收目標只在本文件「版本驗收標準」維護，一個版本一個小節；使用者操作在 [README](../README.md)，各檔案用途、改動位置與每月更新命令在 [repo-map.md](repo-map.md)，設計在 [architecture.md](architecture.md)，尚未決定的延伸設計在 [design-questions.md](design-questions.md)，驗收證據留在對應 issue、PR 描述與 CI。

- **Must**：MVP 必備，缺一項就不算完成。
- **Should**：MVP 之後優先做。
- **Could**：有餘力再做。
- **Won't**：這個版本不做，並寫明原因。

Must 列的證據：PR 流程建立前（PR #1 之前）的項目直接提交到 `main`，以 commit 代碼為證：`1d735fc`（需求與架構文件、公式登記檔、設定檔、CI）、`215250b`（白名單式子解析器、計算引擎、預調度轉接、單一網址雙分頁介面與測試）、`ec2a9b0`（公開網址說明）。

## P13 價差標準檢討：業務邏輯

本節記錄 v1 已實作邏輯；v2 的重新選窗與標準／自訂模式差異見下方「v2」驗收目標，不表示以下現況已完成遷移。

| 步驟 | 邏輯 | 使用者可調 |
|---|---|---|
| 1. 資料 | 讀 T6 的每日摘要：每天的最佳計畫，每個循環記錄價差與淨收益；資料不完整的日子排除並列出日期 | 起訖日 |
| 2. 逐循環套用 | 每個循環的價差 ≥ 標準才執行，不達標的循環跳過；當日淨收益＝執行循環的加總 | 試算標準（不寫入設定檔） |
| 3. 掃候選標準 | 0 到期間內最高價差，每 1 AUD/MWh 一個；輸出執行天數、淨收益、錯過的天數與收益、保留率（淨收益 ÷ 最高淨收益） | N/A |
| 4. 保留範圍 | 保留率 ≥ 門檻的標準構成保留範圍；目前標準在範圍內為「維持」，高於上限為「建議下調」 | 門檻（預設 99%） |
| 5. 成本參考 | 損益兩平價差＝充電均價 ×（1 ÷ 來回效率 − 1）＋ 損耗成本 ÷ MLF；只作說明，不限制保留範圍 | 來回效率、損耗成本 |
| 6. 可信度 | 有效日少於 60 天標「樣本不足」；只涵蓋一個季節標「季節限制」 | N/A |

限制：每日摘要用事後電價、沒有預測誤差，門檻越低收益只會相同或更高，所以不會出現「建議上調」；要納入預測誤差見 T12。P14 完成前，只排除資料不完整的日子，不排除事件日。

## 版本驗收標準

本節是所有版本可驗收目標的唯一來源，一個版本一個小節（`### v1`、`### v2`…），保留舊版本，不以新版本覆寫舊版本標準。新版本開工時，先在這裡新增小節並列出範圍與標準，再開對應的驗收 issue。設計細節在 [architecture.md](architecture.md)，不得另建一份平行版本驗收清單。

| 規則 | 內容 |
|---|---|
| 這裡寫什麼 | 版本範圍（納入哪些需求編號）、每條標準「怎樣算通過」、證據要放哪裡 |
| 這裡不寫什麼 | 驗收證據本身（截圖、數值、日誌）：留在驗收 issue 留言、PR 描述與 CI，這裡只放連結 |
| 延伸設計 | [design-questions.md](design-questions.md) 的條目不屬於任何版本、不阻擋驗收；決定要做時，先轉成上方需求表的一列，再寫進下一版的小節 |
| 驗收中發現的 bug | 另開 issue；影響 Must 需求時阻擋該版本，其餘記為已知限制。已納入該版的驗收標準若未通過，仍阻擋該版完成，不因需求原為 Should 而豁免 |
| 完成判定 | 該版本每條標準都「通過」且附證據連結，才把版本狀態改成「已完成」 |
