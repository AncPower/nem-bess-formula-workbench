# v2 正確性＋效能原型計畫

狀態：2026-10-21 Ava 同意將本計畫補入 repo；原型程式、測試與量測尚未交付，沒有實測結果。本文件定義原型做法，不是第二份版本驗收清單；v1／v2 所有可驗收目標只在 [requirements.md](requirements.md)。使用者用途、業務情境及防錯設計見 [README](../README.md)。

## 1. 為什麼先做原型

v2 要讓使用者改成本、門檻或公式後，重新找到值得執行的排程，並用完整歷史價格比較策略。原型先回答：完整計畫評分會不會漏掉較好的答案，以及資料量增加後算不算得動。

它不直接增加正式站功能；原型通過不等於 v2 完成，Node 速度也不等於瀏覽器驗收通過。

## 2. 業務問題如何對應實驗

| 使用者想知道 | 原型如何驗證 |
|---|---|
| 多做一次是否足以抵銷損耗？ | D1 單循環 A$70、雙循環 A$60 時必須選單循環 |
| 舊機會不達門檻，還有別的可做嗎？ | 兩個價差 3 的小循環不達門檻 4，但價差 5 的大循環可執行時，必須找出大循環 |
| 改公式會不會真的改排程？ | 使用會改變排序的非線性計畫目標，對照完整窮舉，不只改顯示值 |
| 修改策略後，能否重算半年歷史？ | 量測 180 日逐日重選的時間、候選量與記憶體，不拿固定窗口重算代替 |
| 門檻檢討能否維持完整搜尋？ | 量測多門檻乘上多日的重選成本，辨識可重用工作及超限邊界 |

## 4. 搜尋怎麼做

1. 驗證價格順序、連續性、有限數值、設備規格及循環上限。容量／功率必須對應正整數個 30 分鐘時段，不用四捨五入改設備時長。
2. 產生全部合法零、單、雙循環計畫：每循環先充後放、連續滿功率，兩循環依序且不重疊；不按舊價差預選前幾名。
3. 各循環交共用引擎計算收益與執行判斷；包含等待循環的計畫不能勝出，合法子計畫另行比較。
4. 每個完整計畫經共用彙總計算指定目標。預設 `daily_net_revenue`；自訂目標不能假定等於循環分數加總。空計畫也由引擎求值，不硬編碼為零。
5. 比較目標值，按共用浮點容忍及同分規則決定結果。同分優先少循環，再依充放電起點取較早；實作時明列比較規則與測試。

先建立可檢查的完整搜尋基線，再加入不改答案的快取。循環結果快取、公式解析重用等方式必須先確認與現有引擎介面相容；每次加速都重新跑獨立窮舉對照。

不得用局部最佳或舊收益分數剪枝，除非有針對目前目標的正確性證明；任意自訂目標未必單調或可加總。搜尋未完成、超限或中止，不能稱為最佳答案。

## 5. 正確性證據分三層

### 人工可驗算的反例

測 D1 損耗與門檻案例、無正收益選空計畫、負電價、平價、同分、資料不足、設備時長不能整除、關鍵公式錯誤。D1 的價格及設備設定依 [設計問題紀錄](design-questions.md) 建立可重現 fixture，不只比較程式自己產生的預期值。

### 獨立窮舉對照

測試另寫簡單的計畫列舉與比較，不呼叫原型候選產生或排序函式。對小資料逐一比最佳目標值與計畫，並加入固定亂數種子覆蓋不同價格型態與循環時長。

兩邊可共用公式引擎，所以對照證明的是搜尋不漏解與排序一致，不是獨立證明引擎沒有任何錯誤。公式數值仍用人工案例及既有引擎測試補足。

### 自訂目標真的改變排序

加入例如 `-(executed_cycle_net_revenue - target_revenue)^2` 的測試目標，明確提供 `target_revenue` 測試輸入，讓較高總收益未必勝出。不能只用正收益平方這種可能保留原排序的轉換。

修改效率、損耗、門檻、執行判斷及目標後，測最佳窗口確實可能改變；確認沒有沿用舊排程。關鍵公式錯誤不得當零分或略過候選後仍宣稱最佳。

## 6. 效能量測矩陣

| 工作 | 變因與觀察 |
|---|---|
| 單日／單段預調度搜尋 | 48 時段基準及明確記錄的較長範圍；循環上限 1／2、不同合法循環時長，包含短循環壓力案例 |
| 180 日逐日歷史重選 | 每日 48 時段，記錄日別分布與整體耗時，不把一天結果複用 180 次冒充完整重算 |
| 多門檻歷史檢討 | 改變候選門檻數，記錄各門檻逐日重選的總成本；不退回原窗口篩選 |
| 目標公式差異 | 預設淨收益與改變排序的非線性目標，分別量測 |
| 快取與設定變更 | 冷／暖快取分開，另測改門檻、設備或公式後的快取失效與重算 |

記錄 commit、Node／瀏覽器版本、作業系統、可取得的 CPU／記憶體資訊、資料來源與雜湊或種子、參數與公式、候選循環／計畫數、引擎求值次數、快取狀態、重複次數及耗時分布、記憶體指標與是否完整完成搜尋。記憶體須說明是抽樣峰值、堆積用量或程序用量，不混為同一指標。

先做暖機，再多次量測；暖機不混入正式統計。設定安全工作量／時間上限時必須明示，逾限記為未完成，不外推為已量完的時間。

## 7. 測試資料與環境限制

合成資料用於固定反例與壓力測試；180 日合成資料必須標示，不稱為 AEMO 真實歷史驗證。真實資料需先確認公開來源、完整性與取得方式；若拿不到，明列未驗證，不以合成資料替代後隱藏限制。

目前只確認可用 Node 22 執行，未有原型實測。執行環境沒有網際網路連線，不能假設可直接下載 AEMO 或 clone repo；可透過已連接的 GitHub 存取所需檔案，但歷史摘要不等於完整價格。真實資料無法取得時不因此修改本次範圍去建置完整資料發布管線。

Node 結果只支持該執行環境的成本判斷；瀏覽器 JIT、Worker 通訊、畫面回應與正式端到端驗收另外記錄。未測就標未測，不宣稱瀏覽器已可接受。

## 8. 結果應支持哪些決定

結果報告須回答：人工反例、獨立對照與自訂目標哪些通過；單日、180 日與門檻掃描耗時多少；瓶頸是計畫數、引擎求值還是重複工作；安全快取是否值得保留；是否需要 Worker、支援期間與掃描量限制。

提出效能門檻供 Ava 核准，不自行把量測或建議當核准。只有核准後，才在 [requirements.md](requirements.md) 的 V2-11 補正式數值；本文件不另訂通過標準。

成本若過高，提出縮小支援範圍或調整設計的選項，不偷偷改成近似搜尋。原型成功只表示核心的正確性及成本有證據；價格發布、歷史介面、分享、取消流程與正式站驗收仍需後續實作。
